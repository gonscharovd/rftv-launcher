# Правила работы ИИ и разработчиков

## Обязательный старт

1. Начать с [00_START_HERE.md](00_START_HERE.md), затем прочитать релевантные документы.
2. Проверить фактические main HEAD, ветки, PR, последние commits, CI и stable Release.
3. Изучить реализацию и историю кода до изменения. Не просить Product Owner о сведениях, которые можно получить из репозитория.
4. Сформулировать краткий scope и безопасный план; продолжать самостоятельно до реального блокера.

## Архитектура и код

- Сохранять Kotlin + Android Views, один app module и minSdk 24 без согласования изменения концепции.
- Сначала читать существующий код; не переписывать большие файлы ради эстетики.
- Не добавлять фиктивные переключатели или функции. Если OEM/API не поддерживает действие, показывать честный fallback.
- Проверять API level, ABI, разрешения и OEM/StarOS отличия.
- UI обязан работать с DPAD, OK/Enter и Back: начальный фокус, переходы, диалоги, возврат фокуса, скролл.
- Избегать тяжёлого blur, ненужных перерисовок и синхронной сетевой работы.
- Сохранять пользовательские настройки и обратную совместимость OTA.

## TV Manager / безопасность

- Не удалять системные пакеты и не отключать их автоматически.
- Не делать выводы о слежке/записи/передаче по одному имени пакета или permission.
- Reference profiles не универсальны; сверять SDK, board/hardware и device/product.
- Перед любыми потенциальными package actions необходимы доказательства привилегий, предпросмотр, сохранение точного исходного состояния, журнал, проверка зависимостей, поэтапное применение и rollback. Если безопасный механизм недоступен — оставаться read-only.
- Не выполнять ADB диагностику, если она не запрошена.

## Git и PR

- Работать в отдельной ветке от актуального main.
- Не перезаписывать чужие/пользовательские изменения; не force-push без строгой необходимости.
- Не менять main напрямую.
- Делать небольшие логические коммиты с понятными сообщениями.
- Создавать PR с описанием scope, тестов, рисков и screenshots/logs при необходимости.
- Не сливать PR без разрешения Product Owner. Не публиковать релиз автоматически без проверки всех release gates.

## Сборка и тестирование

- Выполнять unit tests, Android Lint, сборку и доступные static checks.
- Проверять CI по конкретному commit SHA.
- Разделять в отчёте: исходники/локальные тесты; CI; подписанный Release APK и проверка артефакта; физическое тестирование.
- Не говорить, что ТВ проверен, пока пользователь не подтвердил.
- Debug APK не устанавливать на целевой ТВ; приёмка — подписанный stable Release через OTA.
- Любая новая версия должна увеличить versionCode и использовать постоянный Release signing identity.

## Секреты и OTA

- Никогда не выводить keystore, пароли, токены, secrets или приватные ключи в документацию, логи, PR или чат.
- Не заменять, не создавать заново и не терять постоянный Release key.
- Проверять package, versionCode/versionName, minSdk/targetSdk, ABI, размер, SHA-256, сертификат и соответствие опубликованного asset собранному APK.
- Не перезаписывать опубликованный Release. Draft можно обновлять только в рамках безопасной логики workflow.
- Установка только штатным Android механизмом с подтверждением пользователя; учитывать отказ и ошибки.

## Базы данных и внешние сервисы

На дату аудита в репозитории нет отдельной БД, миграций или backend/API server. Не вводить внешнюю инфраструктуру без продуктового/архитектурного обоснования. Для сетевых интеграций предусматривать timeout, retry с пределами, cache, offline и обработку некорректного ответа.

## Документация и передача

- Поддерживать project-memory при каждой логической задаче.
- Не дублировать детали без нужды; ссылаться на первичные файлы.
- Разделять подтверждённые факты, предположения и неизвестное.
- Перед завершением обновить CURRENT_STATE, TASKS, SESSION_HANDOFF; проверить ссылки и согласованность.
- Не объявлять GitHub write/PR/CI успешными, пока API/CI не подтвердили результат.
