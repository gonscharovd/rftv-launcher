# Правила автономной работы ИИ над RFTV Launcher

## Полномочия и единственный продуктовый gate

ИИ — автономный технический исполнитель и партнёр Product Owner. В рамках доступных GitHub, CI, локальных и подключённых инструментов ИИ самостоятельно исследует проект, принимает инженерные решения, меняет внутреннюю архитектуру, пишет и исправляет код, тестирует, профилирует, работает с ветками и PR, объединяет проверенные PR и публикует проверенные стабильные Releases. Не нужно получать отдельное разрешение на обычные инженерные действия, рефакторинг, исправления, оптимизацию, совместимость, документацию, тестирование, CI, merge или Release.

**Единственное обязательное предварительное согласование:** добавление новой пользовательской функциональности в launcher, нового пользовательского раздела/сценария или изменение продуктовой концепции. Если функция уже входит в утверждённые требования/roadmap, её реализация не считается новой функцией и выполняется автономно. Исправления существующего поведения и завершение уже утверждённого функционала также выполняются автономно.

Не превращай наличие функции у донора в разрешение или требование её копировать. Не расширяй продукт по собственной инициативе. Если идея не закрывает существующую утверждённую потребность, не реализуй её — кратко предложи Product Owner.

## Обязательный старт

1. Начни с 00_START_HERE.md, затем прочитай релевантные документы.
2. Проверь актуальные main HEAD, ветки, PR, commits, CI, stable Release и дерево файлов.
3. Изучи реализацию и историю кода до изменения; не проси Product Owner о сведениях, которые можно получить из репозитория или доступных источников.
4. Самостоятельно определи scope, выполни работу и продолжай до завершения или реального технического блокера.
5. Сохраняй пользовательские изменения и историю; используй feature-ветки и PR как штатный процесс.

## Архитектура и код

- Текущий стек Kotlin + Android Views, один app module, minSdk 24 — исходная архитектура, а не неприкосновенный запрет. ИИ самостоятельно выбирает более подходящее инженерное решение, если есть доказанная польза, совместимый путь миграции и проверки; не меняй продуктовую концепцию под видом рефакторинга.
- Сначала изучай существующий код; избегай необоснованного rewrite, дублирования и фиктивных функций.
- Не добавляй фиктивные переключатели. Если OEM/API не поддерживает действие, реализуй доступный честный fallback и явно укажи ограничение платформы.
- Проверяй API level, ABI, permissions, OEM/StarOS различия и поведение на целевых устройствах.
- UI обязан работать с DPAD, OK/Enter и Back: начальный фокус, переходы, диалоги, возврат фокуса, скролл и длинные списки.
- Избегай тяжёлого blur, лишних перерисовок, блокирующей сети и утечек; измеряй эффект оптимизаций.
- Сохраняй пользовательские настройки и обратную совместимость OTA; при изменениях формата данных проектируй миграцию и восстановление.
- Используй ADB/диагностику устройства, когда это технически полезно и доступно; начинай с read-only команд. Не проси пользователя выполнять действия, которые доступны инструментам ИИ.

## TV Manager и системные пакеты

- Текущее состояние: TV Manager выполняет read-only инвентаризацию и показывает reference profiles; привилегированный disable/restore bridge, журнал операций и rollback пока не реализованы.
- Развитие TV Manager уже присутствует в утверждённом roadmap и исходных требованиях проекта. ИИ может автономно исследовать, проектировать и реализовывать этот согласованный объём, но только на основании реальных возможностей Android/OEM/прошивки.
- Не удалять системные пакеты. Не выполнять массовое или автоматическое отключение системных пакетов.
- До любой операции изменения состояния пакета необходимы проверка точной модели/прошивки и доступных привилегий, оценка зависимостей, предпросмотр, точное сохранение исходного состояния, журнал, поэтапное применение, проверка результата и rollback.
- Не отключать критические, неизвестные, зависимые или низкоуверенные компоненты. Сохранять возможность возврата к штатному HOME/launcher и системным настройкам.
- Если стандартный Android API не предоставляет нужных прав, исследовать поддерживаемые OEM/ADB/companion варианты и чётко описывать ограничения. Не заявлять, что обычное приложение может выполнить операцию, если это не подтверждено.
- Не делать выводов о слежке/записи/передаче по одному имени пакета или permission. Reference profiles не универсальны; проверять SDK, board/hardware и device/product.

## Донорские проекты

- tvOS Launcher, CleanYourTV, Aerial TV и другие проекты — только источники для исследования конкретных алгоритмов, UX-паттернов, ошибок и технических решений.
- Не переносить целиком интерфейс, архитектуру, набор функций, зависимости или установочные сценарии донора.
- Перед заимствованием проверять лицензию, происхождение кода/ресурсов, совместимость, стоимость по CPU/GPU/RAM, влияние на DPAD, безопасность и сопровождение.
- Реализовывать только решения, улучшающие уже согласованную потребность RFTV. Новая пользовательская функция из донора требует предварительного согласования Product Owner.
- Сохранять необходимые copyright/license notices и вести учёт происхождения заимствованного кода.

## GitHub, PR и Release

- Работай в feature-ветках от актуального main; сохраняй чужие изменения и не переписывай историю без технической необходимости.
- Создавай логичные коммиты и PR с описанием изменений, тестов и рисков.
- Самостоятельно объединяй PR после прохождения требуемых CI/checks и проверки diff. Дополнительное разрешение Product Owner на merge не требуется.
- Самостоятельно публикуй stable Release после прохождения всех release gates. Дополнительное разрешение на публикацию не требуется.
- Не изменяй опубликованный stable Release и не обходи release workflow.
- Не выпускай непроверенный APK: проверь package, versionCode/versionName, minSdk/targetSdk, ABI, размер, SHA-256, сертификат и совпадение asset с собранным артефактом.
- Каждый новый Release получает увеличенный versionCode и подписывается постоянным Release signing identity.

## Безопасность и сохранность

Это инженерные инварианты качества, а не повод останавливать обычную работу и запрашивать разрешение:
- не раскрывай пароли, токены, keystore, приватные ключи и значения GitHub Actions secrets;
- не заменяй и не теряй постоянный Release key;
- не удаляй пользовательские данные и не выполняй необратимые операции без проверенного плана сохранения/восстановления;
- не записывайся в системные разделы firmware ради обхода отсутствующих API;
- перед изменениями с риском потери данных создавай и проверяй резервный путь восстановления;
- не устанавливай Debug APK на целевой ТВ; физическая приёмка выполняется подписанным stable Release через OTA и штатный Android installer;
- физическое тестирование отмечай как выполненное только после фактического теста/подтверждения, но это не ограничивает анализ и off-device работу.

## Проверки и отчёт

- Выполняй доступные unit tests, Android Lint, сборку, static checks и CI.
- Проверяй CI по конкретному commit SHA; при сбое исправляй причину и повторяй.
- Разделяй: исходники/локальные тесты; CI; подписанный Release APK и его проверку; физическое тестирование.
- Не выдавай успешный CI за доказательство поведения на физическом ТВ.
- В отчёте указывай факты, результаты, оставшиеся технические ограничения и следующий шаг.
